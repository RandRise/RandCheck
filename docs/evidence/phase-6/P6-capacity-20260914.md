## Verified boundaries

- Two independent restricted API hosts race for the same organization capacity;
  only one upload is admitted, and the loser's source is removed. The same boundary
  holds when the database defaults to Repeatable Read: admission explicitly uses
  Read Committed and reads usage after obtaining its organization lock.
- A restricted worker completes and commits its System audit event while another
  transaction holds the capacity organization lock. `FOR NO KEY UPDATE` permits
  foreign-key checks without giving up serialization of admissions.
- Missing required policies reject upload before storage/scanning. Existing policies
  remain enforced when a local host sets RequirePolicy false. Production and Staging
  force policy requirements even when configured false.
- Organizations have independent limits. Reprocessing races admit one job, preserve
  run history and add no source bytes. RetryScheduled still occupies capacity; worker
  completion frees it. A lowered storage limit does not block zero-byte reprocessing.
- Pending source deletion remains charged through a forced authorization-audit
  outage; successful retry removes the source, completes deletion and frees bytes.
- Private policy creation/status/update bind to the exact database and policy version.
  A stale update refuses, and an audit outage rolls back the policy/version change.
- API policy writes fail under the real restricted login. Database checks reject
  invalid limits, organization remapping, deletion and truncation. Empty downgrade
  and reapply succeed; populated downgrade refuses.

## Corrections and limits

The initial deletion fixture targeted an obsolete audit action; it now faults the
actual `document.source-purge-authorized` boundary. The API storage-rejection fixture
now also supplies its fake queue, since upload preflight legitimately queries the
queue store before storage. Raw initial failures are preserved. Successful final
checks supersede those cases without weakening the expected application behavior.

The broader PostgreSQL run preceded the final isolation/lock refinements. Its capacity
cases are excluded from the aggregate and replaced by the final capacity-only run;
changed theory names do not count twice. Only final successful outcomes count.

These are registered-source quotas, not hard filesystem limits. Staging, orphan files,
derived data, backups and journals are excluded. Recovery of untracked upload files
and independently verifying capacity-policy freshness after restore are next. Enterprise
deployment must apply migration 19, provision policies and reapply the API allowlist.
Full Phase 6 acceptance still requires the outstanding deployment and operational work.
