# A02: Staff and Admin only

October 19, 2026. Approved source change; real account conversion and manual
acceptance remain pending. This supersedes the earlier
[A01 label-only approach](staff-role-20261019.md), whose evidence is retained.

## Scope and behavior

Staff handles document work. Admin includes Staff powers and user, audit, retention
and deletion administration. Active/disabled is status. Current domain, API,
permissions and screens no longer accept Viewer, Reviewer, Operator, None or a
separate administration flag. Unknown roles, numeric role strings, missing active
status and obsolete request fields are rejected. Backend permissions, active actor
checks, organization boundaries, account versions and last-Admin protection remain.

New accounts require an explicit role choice. Existing documents, reviews, frozen
results, old audit descriptions and retry ledgers are not rewritten or deleted.
Arabic help is retained. G02/G03, dashboard, Owner and full export remain separate.

## Migration boundary

The configured localhost:55432 database could not be reached. No real membership
inventory was obtained, no real accounts were approved for promotion and no live
migration was run. `outputs/two-roles-20261019/inventory.json` records the failure.

The guarded migration locks membership, actor, organization and identity inputs,
then compares the exact approved inventory inside the schema transaction. The
inventory identifies each account, Microsoft tenant/object IDs, old and new
rights, versions and both active states. Missing, extra, duplicate or changed
entries stop conversion. Former limited users would gain powers: their conversion
requires explicit review. Former None accounts without administration become
disabled; administration-only accounts would gain document access as Admin and
require explicit approval. Inactive actors
and memberships remain inactive. Audit insertion and conversion commit together.
Populated role downgrades are refused; empty disposable databases may roll back.

### Cutover after the database is available

1. Back up the database and confirm a restore plan. Stop old API/worker writes for
   the coordinated cutover; old and new role contracts cannot run together.
2. Set PostgreSQL `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER` and credentials through
   the normal secure environment. Do not put passwords in commands or evidence.
3. Run `.venv/Scripts/python.exe tools/migrate-access-roles.py inventory --plan <private-plan.json>`
   with `--psql <installed-psql-path>` when needed. This is read-only and refuses
   to overwrite an earlier plan. Keep account names/identity details private.
4. Review every change with the owner. If a person should not gain access, stop and
   resolve that account using the old authorized membership workflow, then make a
   fresh inventory. Do not edit snapshot values to bypass the exact comparison.
5. Only after actual approval, set the plan's `approved` value to `true` and run
   the same tool with `apply --plan <private-plan.json>`. It uses the versioned
   `tools/migrate-access-roles.sql`, checked against the EF migration in tests.
   An optional `--script` must be an exact copy; arbitrary scripts are refused.
6. If execution fails or the connection drops, inspect migration history, schema
   and new audit events read-only before retrying. A lost response cannot prove
   rollback. Start the new API/web only after confirmed schema conversion, then
   verify representative Staff/Admin and disabled accounts with real identity.
